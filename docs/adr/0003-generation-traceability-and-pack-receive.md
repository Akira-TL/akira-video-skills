# Generation 与 Shot 解耦，并以 G / I / take 追溯生成尝试

AI 模型的生成任务与最终镜头不是父子关系：一次生成可以包含多个计划 / 实际镜头，一个最终镜头也可以由多个生成结果拼接。因此 Generation 独立于 Shot 保存；G / I / take 只记录生成意图、正式输入和实际输出，最终采用关系由消费结果的资产、镜头、音频或剪辑记录维护。

## Generation 模型

- **G（Generation）**：一项有明确目标的生成任务，不是一次模型调用；可以生成图片、视频、声音或音乐。
- **I（Input Version）**：该 G 的一个正式输入版本，拥有唯一 Prompt 正文、实际参考文件和必要设置。正式 outbound 包一旦生成 / 交付即冻结；修改 Prompt、参考版本或关键设置产生新 I。
- **take**：按某个 I 返回的一个可独立评审候选结果。同一 G 内 `takeNN` 持续递增，切换 I 不重置、历史编号不复用；项目编号不承诺反映平台生成顺序。普通情况下一个 Take 就是一个媒体文件；只有候选天然由视频、音轨、字幕等配套文件共同构成时，才把这些文件作为同一 Take 的文件集合。

同一输入再次 Generate 产生新的 take，不产生新 G；同一目标下修 Prompt / 换参考产生新 I；生成目标本身改变才新建 G。用户在平台实际修改 Prompt、素材或设置时，返回后必须按真实输入补记新的 I，再关联 take；实际输入无法确定时先保留待核对，不能硬挂回原 I。

## 作用域

G 在所属范围内局部编号：

- 视频内部可写 `G003`；
- 跨视频引用写 `V001/G003`；
- 跨视频共享资产生成写 `shared/G003`。

正式路径可位于 `video/videos/V001_*/generations/G003*/` 或 `video/shared/generations/G003*/`，但引用解析只认作用域 + ID，不拼接或持久依赖人类助记后缀。

## 正式输入与结果

完整 Prompt 只维护在对应输入版本的 Prompt 文件；`GENERATION.md` 记录目标、计划覆盖范围、I、Prompt pointer、实际参考文件及职责、必要设置、返回 take 与 Review 结论，不复制 Prompt 正文，也不维护模糊的“current take”。共享人物 / 地点 / 道具资产如果由该 G 生成，只在资产记录中引用这一正式 Prompt 来源，不再保存一份重复的资产 Prompt 正文。

实际投入模型的二进制输入必须保留其真实版本，不能用 SHA 替代文件保存，也不要求为 Generation 额外计算 SHA。参考图片通常不做手工裁剪 / 压缩链；不合适时优先重新生成。少见情况下确实人工处理并用于生产，则把处理后的图片保存为新的正式资产版本，再由 I 引用。

Generation 可以记录计划覆盖 `SH010–SH030`，这是生成意图；尚未进入正式剪辑时，唯一 Shot 表可以记录计划 / 候选采用来源。建立正式剪辑时间线后，最终用了哪条 Take、哪个时间范围、同一 Take 是否复用、一个 Shot 是否由多个来源拼接，只由剪辑记录维护；Shot 保留叙事意图并引用对应剪辑项，不同步第二份实际剪辑结果。图片 Take 若被采用为角色参考，由角色资产记录维护具体版本来源与当前默认；音乐 Take 的最终使用由音频 / 剪辑记录维护；G 不再复制 selected 状态。

Take Review 可以记录 `unchecked / usable / revision-needed / rejected` 和实际问题范围，例如“6.2 秒后人物身份漂移”。这些结论针对生成目标，不意味着整条媒体所有帧都可用或都不可用。

## 自包含 outbound pack

每个给用户外部生成的包必须直接可执行，至少提供唯一 Prompt、真实存在的上传素材、编号 / 职责、明确上传顺序、必要设置和返回要求；不能让用户再去 `shared/` 手工找引用文件。

临时目录带上 G 的作用域与 I，避免不同视频的局部 G 编号碰撞：

```text
.tmp/V001/G003_I02/
.tmp/shared/G003_I02/
```

这些目录是可重建派生物，不是正式记录。正式 G / I 必须足以说明当时交付的 Prompt、参考版本和设置；临时包不反过来成为事实源。

## Receive 必须幂等且自动收尾

返回文件首先依靠可靠的 scope / G / I 信息确定归属，不能靠画面内容猜。归属确认后，一批候选可以在正式接收时依次分配新的 take，保留原文件名或平台结果标识用于辅助追溯；take 编号只表示项目身份。

正常 Receive 顺序是：核对归属 → 保存全部返回候选 → 建立 take 与实际 I 映射 → 核验正式记录完整 → 检查临时包没有尚未正式保存的唯一信息 → 自动清理该版本临时目录及对应派生 zip。唯一信息包括用户在外部流程实际修改后的 Prompt、替换的参考文件、真实使用设置和返回结果；这些内容若与原 I 不同，必须先补记真实 I / 正式资产或保留待核对，不能只因为媒体结果已复制就删包。失败候选也先正式保存，再进入 Review；接收动作不因为质量不好而丢结果。

Receive 必须可以安全重跑：

- 同一返回批次重复执行不会产生重复 take，也不会覆盖已有结果；
- 中途失败后重跑会从已有正式记录继续；
- “正式接收成功但临时清理失败”只能重试清理，不能重新导入或重新编号；
- 同一个 I 以后仍可接收新的候选，上一批临时包已清理不代表 I 被关闭；
- 返回数量只有在事先明确约定时才校验，不凭空假定候选数。

如何识别“同一返回批次的重试”属于接收脚本内部实现，不引入需要用户管理的新领域编号。临时清理必须精确针对已核验的那个 scope / G / I 包，不使用模糊文件名批量删除其他包。
