# 媒体文件生命周期

目标是让长期项目保持可读，同时避免误删唯一素材。

## 1. 长期必须保留

除非用户明确要求删除，否则长期保留：

- 已确认的角色 / 场景 / 产品 / 道具参考；
- 正式设计文件与长期提示词；
- 当前采用镜头对应的原始生成结果；
- 当前后期工程；
- 正式成片 / 交付文件；
- 无法重新获取的用户原始素材。

## 2. 可以按需保留

以下内容是否长期保留由项目价值 / 存储成本决定：

- 未采用但很接近的生成结果；
- 备用配音；
- 设计候选；
- 审片导出；
- 与当前方案不同但未来可能复用的参考。

如果保留，必须能看出用途；不要把所有失败结果都无限堆在正式目录。

## 3. 默认可清理

确认不再需要且没有唯一信息时可以清理：

- 一次性生成包；
- 未选中的图片 / 声音候选；
- 明显失败且没有分析价值的生成结果；
- 可重建代理文件；
- 缓存；
- 临时转码；
- 临时压缩包。

## 4. 删除前检查

任何清理动作至少确认：

- 文件不是当前采用结果；
- 文件没有被后期工程唯一引用；
- 文件不是用户唯一原始输入；
- 包内没有尚未归档的返回结果；
- 包内没有唯一提示词 / 唯一参考素材；
- 当前失败结果没有被保留用于后续问题诊断。

## 5. 用户返回的原始素材

用户上传 / 返回的文件如果需要长期保留，先复制 / 整理到正式归属位置，再删除一次性包或临时返回位置。

不要让 `.tmp/.../returns/` 里的文件成为项目唯一正式副本。

## 6. 后期缓存与代理

Premiere Pro、After Effects、DaVinci Resolve 等软件的缓存、代理、预览渲染通常是可重建文件。

这些文件按软件和本机工作流管理，不要求进入 Git，也不应被误认为正式交付。

如果项目必须跨机器移动，优先使用对应后期软件的媒体管理 / 项目收集功能，而不是手工猜哪些缓存要复制。

## 7. Git 边界

Git 主要保存文本规则、提示词、项目定义和适合版本控制的小型配置。

大型图片、视频、音频是否由 Git、Git LFS 或其他项目存储机制管理，由当前项目自己的版本策略决定；Akira Video 不擅自引入新的大文件存储系统。

## 完成标准

项目长期保留真正不可替代和当前有效的素材；临时包、失败垃圾和可重建缓存不会无限积累；删除前不会误伤唯一输入或当前采用媒体。
